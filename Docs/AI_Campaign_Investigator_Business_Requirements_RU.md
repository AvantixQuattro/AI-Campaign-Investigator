# AI Campaign Investigator
## Бизнес-требования и спецификация исследовательского проекта

**Статус документа:** черновик для реализации  
**Тип проекта:** исследовательский / техническая оценка ИИ  
**Основная аудитория:** потенциальный работодатель, CTO, инженерное руководство, руководство по ИИ/ML  
**Основная цель:** оценить измеримую ценность AI-агента для открытого исследования бизнес-задач программы лояльности  
**Исходный набор данных:** dunnhumby — The Complete Journey  
**Целевая архитектура:** PostgreSQL + pgvector, Python Agent, LLM API, Web UI

---

## 1. Резюме

Этот исследовательский прототип предназначен для определения того, даёт ли **AI-агент измеримую ценность по сравнению с традиционной SQL/правиловой аналитикой и традиционными ML/статистическими подходами** при изучении эффективности программ лояльности и формировании маркетинговых гипотез, основанных на доказательствах.

Система под названием **AI Campaign Investigator** будет помогать маркетологу отвечать на вопросы вроде:

> «Почему эффективность кампании по возврату клиентов снизилась за последние три месяца и что следует исследовать дальше?»

Агент не заменяет детерминированную аналитику или ML. Вместо этого он оркестрирует специализированные аналитические возможности:

- количественный анализ на SQL;
- статистические/ML-модели, когда они уместны;
- семантический поиск исторических знаний о кампаниях;
- многошаговое исследование;
- формирование гипотез;
- синтез доказательств;
- формирование рекомендаций.

Ключевой исследовательский вопрос:

> **Может ли AI-агент существенно повысить скорость, качество, полноту и практическую полезность открытых исследований программ лояльности по сравнению с традиционными аналитическими подходами?**

Проект явно предназначен для проверки этой гипотезы, а не для заранее принятого предположения о превосходстве ИИ.

---

# 2. Исследовательские гипотезы

## 2.1 Основная гипотеза

**H1**

> Для открытых исследований бизнес-задач лояльности, требующих синтеза структурированных данных о клиентах/кампаниях и неструктурированных бизнес-знаний, AI-агент может давать более качественные и/или быстрые инсайты, чем детерминированные SQL/правиловые и традиционные ML/статистические подходы.

## 2.2 Нулевая гипотеза

**H0**

> AI-агент не даёт существенного преимущества над традиционными SQL/правиловыми и ML/статистическими подходами для выбранных задач исследования программы лояльности.

## 2.3 Важная оговорка

Проект **не** исходит из того, что ИИ — лучшее решение для каждой аналитической задачи.

Для детерминированных расчётов ожидается превосходство SQL.

Для предиктивных задач, таких как склонность к оттоку, прогноз отклика или оценка uplift, традиционный ML может быть предпочтительнее.

Исследование сосредоточено именно на задачах, включающих:

- неоднозначные бизнес-вопросы;
- итеративное исследование;
- разнородные источники информации;
- неструктурированные маркетинговые знания;
- формирование гипотез;
- выбор последующих шагов исследования.

# 3. Бизнес-проблема

Организация, работающая с программой лояльности, обычно располагает несколькими источниками информации:

- транзакции клиентов;
- атрибуты клиентов;
- определения кампаний;
- охват кампаний;
- результаты кампаний;
- промоакции;
- сведения о продуктах/категориях;
- результаты экспериментов;
- брифы кампаний;
- гипотезы маркетологов;
- post-mortem-анализы;
- комментарии аналитиков;
- журналы решений.

Традиционные BI-системы очень эффективны при ответе на заранее определённые вопросы:

> Каков был ROI кампании?

> У какого сегмента была наибольшая конверсия?

> Сколько клиентов воспользовались предложением?

Однако бизнес-заказчики часто задают открытые вопросы:

> Почему эффективность снизилась?

> Что изменилось?

> Видели ли мы нечто подобное раньше?

> Что могло объяснить это изменение?

> Что следует исследовать дальше?

> Какие предыдущие эксперименты релевантны?

Для ответа на такие вопросы аналитик обычно вручную должен:

1. интерпретировать вопрос;
2. определить релевантные метрики;
3. сформулировать SQL-запросы;
4. изучить сегменты;
5. сравнить исторические периоды;
6. найти документацию по кампаниям;
7. изучить предыдущие эксперименты;
8. сформулировать гипотезы;
9. проверить гипотезы;
10. подготовить рекомендацию.

Проект исследует, способен ли AI-агент сократить этот ручной аналитический процесс, сохранив фактическую точность и аналитическую строгость.

# 4. Цели проекта

## 4.1 Основные цели

Система должна:

1. Исследовать открытые бизнес-вопросы по программе лояльности.
2. Динамически выбирать подходящие аналитические инструменты.
3. Запрашивать структурированные данные через контролируемые интерфейсы.
4. Искать неструктурированные знания о кампаниях с помощью семантического поиска.
5. Использовать статистический/ML-анализ там, где это уместно.
6. Сравнивать текущие ситуации с историческими кампаниями.
7. Формировать явные гипотезы.
8. Разграничивать факты, выводы, гипотезы и рекомендации.
9. Представлять доказательства для количественных и качественных выводов.
10. Давать практические рекомендации маркетологу.
11. Сохранять проверяемую трассу исследования.
12. Измерять эффективность AI-подхода относительно традиционных базовых подходов.

## 4.2 Второстепенные цели

Проект также должен продемонстрировать:

- модульную архитектуру AI-агента;
- безопасное взаимодействие LLM и баз данных;
- заменяемые наборы данных;
- заменяемых поставщиков LLM;
- инженерные практики, ориентированные на production;
- воспроизводимую оценку;
- измеримую экономику ИИ.

# 5. Границы проекта

## 5.1 Входит в объём работ

MVP будет поддерживать:

- аналитику клиентов программы лояльности;
- анализ эффективности кампаний;
- анализ клиентских сегментов;
- сравнение кампаний;
- поиск исторических кампаний;
- поиск маркетинговых знаний;
- многошаговое исследование;
- формирование гипотез;
- рекомендации, подкреплённые доказательствами;
- статистический анализ;
- опциональные ML-модели;
- трассу исследования;
- оценку относительно традиционных подходов;
- измерение стоимости и производительности;
- веб-интерфейс для демонстрации.

## 5.2 Не входит в объём работ

MVP не будет:

- автоматически запускать кампании;
- изменять записи о клиентах;
- отправлять предложения клиентам;
- принимать необратимые бизнес-решения;
- заявлять о причинно-следственных связях без надлежащих статистических доказательств;
- заменять ML-модель, если ML-модель явно является подходящим решением;
- предоставлять LLM неограниченный доступ к базе данных;
- полагаться на числовые расчёты, сгенерированные LLM, когда доступен детерминированный расчёт.

# 8. Представительные бизнес-сценарии

MVP должен поддерживать десять представительных сценариев.

## Сценарий 1 — Снижение эффективности кампании

> Почему эффективность кампании по возврату клиентов снизилась за последние три месяца?

Ожидаемое исследование:

- установить базовый уровень;
- выявить затронутые сегменты;
- сравнить состав клиентов;
- изучить охват кампании;
- изучить характеристики предложения;
- найти исторические аналоги;
- сформулировать и проверить гипотезы.

## Сценарий 2 — Ухудшение сегмента

> Какие клиентские сегменты демонстрируют наиболее тревожное ухудшение поведения?

Ожидаемый результат:

- затронутые сегменты;
- релевантные метрики;
- величина изменения;
- историческое сравнение;
- возможные объяснения.

## Сценарий 3 — Историческое сходство кампаний

> Возникала ли ранее ситуация, похожая на текущую?

Ожидаемый результат:

- похожие кампании;
- обоснование сходства;
- фактические результаты;
- релевантные выводы.

## Сценарий 4 — Сравнение кампаний

> Почему Кампания A превзошла Кампанию B?

Агент должен сравнить:

- аудиторию;
- предложение;
- время проведения;
- охват;
- поведение клиентов;
- результаты кампаний;
- исторические прецеденты.

## Сценарий 5 — Возможность реактивации

> Какие группы клиентов сейчас представляют наилучшую возможность для реактивации?

Агент может использовать аналитические модели, но обязан объяснить доказательства, лежащие в основе рекомендации.

## Сценарий 6 — Усталость от кампаний

> Является ли усталость от кампаний правдоподобным объяснением снижения отклика?

Агент должен:

- сформулировать гипотезу;
- определить релевантные метрики охвата;
- проверить связь;
- найти исторические доказательства;
- отличать связь от причинности.

## Сценарий 7 — Доказательства предыдущих экспериментов

> Какие предыдущие эксперименты подтверждают или опровергают предлагаемый подход?

Агент должен найти знания о кампаниях и сопоставить задокументированные гипотезы с наблюдаемыми результатами.

## Сценарий 8 — Неожиданное изменение KPI

> Использование предложения выросло, но ROI кампании снизился. Почему?

Агент должен исследовать:

- использование предложения;
- стоимость вознаграждения;
- инкрементальную выручку;
- состав клиентов;
- экономику предложения;
- микс кампаний.

## Сценарий 9 — Поиск маркетинговых знаний

> Что мы исторически узнали о реактивации высокоценных клиентов?

Агент должен синтезировать несколько брифов кампаний, post-mortem-анализов, заметок и результатов.

## Сценарий 10 — Следующее исследование

> Что маркетинговой команде следует исследовать дальше?

Агент должен расставлять приоритеты нерешённых гипотез на основе:

- потенциального бизнес-эффекта;
- доступных доказательств;
- неопределённости;
- возможности проверки.

# 9. Требования к данным

## 9.1 Основной набор данных

В начальной реализации должен использоваться:

**dunnhumby — The Complete Journey**

Набор данных содержит реальные исторические данные в стиле розничной программы лояльности: домохозяйства клиентов, транзакции, кампании, промоакции, купоны и информацию, связанную с кампаниями.

Набор данных статичен. Поэтому прототип должен поддерживать **слой исторического воспроизведения/симуляции**, чтобы данные могли открываться постепенно по смоделированным периодам времени.

## 9.2 Абстракция набора данных

Система не должна жёстко привязываться к идентификаторам, специфичным для dunnhumby.

Логическая модель данных должна разделять:

- канонические бизнес-сущности;
- сопоставления, специфичные для источника;
- загрузку исходных данных;
- аналитические представления.

Система должна позволять в будущем заменить исходный набор данных без перепроектирования агента.

## 9.3 Синтетические маркетинговые знания

Публичный набор данных не предоставляет полного корпуса реальных внутренних маркетинговых брифов, post-mortem-анализов, журналов решений и заметок маркетологов.

Поэтому проект должен создать **слой синтетических маркетинговых знаний**.

Эти документы должны быть явно помечены как синтетические.

Синтетические документы должны быть **основаны на фактах исходного набора данных**.

Примеры:

- бриф кампании;
- гипотеза кампании;
- план эксперимента;
- сводка результатов кампании;
- post-mortem-анализ;
- заметка маркетолога;
- журнал решений.

Количественные утверждения в синтетических документах должны генерироваться из структурированного набора данных или проверяться по нему.

Система никогда не должна представлять синтетические документы как реальные корпоративные документы.

## 9.4 Намеренно противоречивые знания

Набор данных для оценки должен содержать выбранные синтетические документы, в которых зафиксированная интерпретация маркетолога неполна, сомнительна или противоречит структурированным доказательствам.

Пример:

> Гипотеза маркетинговой команды: кампания провалилась, потому что предложение было недостаточно привлекательным.

Структурированные данные могут показать:

- использование предложения выросло;
- стоимость вознаграждения выросла;
- инкрементальная выручка не выросла.

Агент должен выявлять расхождение, а не слепо повторять задокументированную гипотезу.

# 12. Архитектура AI-агента

## 12.1 Роль агента

LLM не является аналитической базой данных и не является системой учёта.

Агент действует как **оркестратор исследования**.

Его обязанности:

1. интерпретировать бизнес-вопрос;
2. определять требуемые доказательства;
3. выбирать подходящие инструменты;
4. оценивать возвращённые доказательства;
5. формулировать гипотезы;
6. выбирать последующие исследования;
7. синтезировать результаты;
8. формировать рекомендации.

## 12.2 Категории инструментов

MVP должен предоставлять ограниченный набор контролируемых инструментов.

### Инструменты структурированных данных

Примеры:

```text
get_campaign_metrics()
get_segment_metrics()
compare_periods()
get_customer_behavior()
get_campaign_exposure()
compare_campaigns()
```

### Инструменты поиска знаний

Примеры:

```text
search_campaign_knowledge()
find_similar_campaigns()
search_postmortems()
search_experiments()
```

### Статистические / аналитические инструменты

Примеры:

```text
analyze_exposure_vs_response()
calculate_segment_change()
run_statistical_test()
```

Точная реализация может развиваться.

```text
Уточнение гипотезы
   |
   v
Следующий вызов инструмента
   |
   v
...
   |
   v
Вывод, подкреплённый доказательствами
```

Таким образом, система представляет собой **Agentic RAG / агента, расширенного инструментами**, а не одношаговое RAG-приложение.

---

# 13. Требования к RAG

RAG должен использоваться именно для неструктурированных или полуструктурированных бизнес-знаний.

Система должна поддерживать семантический поиск по:

- брифам кампаний;
- гипотезам;
- post-mortem-анализам;
- отчётам об экспериментах;
- заметкам маркетологов;
- журналам решений.

RAG не должен заменять SQL в числовом анализе.

Перед формированием окончательной рекомендации агент должен объединить:

```text
Структурированные доказательства
        +
Найденные знания
        +
Статистические/ML-доказательства
```

---

# 14. Требования к взаимодействию с LLM

## AI-001 — Рассуждение, основанное на доказательствах

Агент должен основывать количественные утверждения на результатах инструментов.

## AI-002 — Разделение факта / вывода / гипотезы

Результат должен чётко разграничивать:

- **Факт** — непосредственно наблюдаемый в данных или документах;
- **Вывод** — интерпретация, подтверждённая доказательствами;
- **Гипотеза** — правдоподобное объяснение, требующее дальнейшей проверки;
- **Рекомендация** — предлагаемое действие или следующее исследование.

## AI-003 — Запрет на неподтверждённые количественные утверждения

LLM не должна выдумывать:

- значения KPI;
- количество клиентов;
- результаты кампаний;
- даты;
- статистическую значимость;
- ROI.

## AI-004 — Дисциплина причинности

Корреляция не должна выдаваться за причинность без надлежащих причинных доказательств.

## AI-005 — Цитирование доказательств

Важные выводы должны указывать подтверждающий источник/результат инструмента.

## AI-006 — Недостаточность доказательств

Агент должен явно сообщать, когда доступных доказательств недостаточно.

## AI-007 — Выявление противоречий

Агент должен выявлять конфликты между:

- структурированными данными;
- исторической документацией;
- гипотезами маркетологов.

## AI-008 — Динамическое исследование

Агент должен быть способен выбирать разные пути исследования для разных вопросов.

## AI-009 — Без неограниченного доступа к базе данных

LLM не должна получать неограниченные учётные данные базы данных или произвольный доступ на запись в production.

## AI-010 — Аналитический доступ только для чтения

Доступ к аналитической базе данных MVP должен быть только для чтения с точки зрения агента.

---

# 15. Требования безопасности

Система должна следовать принципам безопасности, ориентированным на production.

## 15.1 Безопасность базы данных

- учётные данные агента к базе данных только для чтения;
- параметризованные запросы;
- отсутствие произвольных операций записи;
- таймаут запросов;
- ограничения размера результатов;
- ограничения ресурсов.

## 15.2 Безопасность LLM

Реализация должна учитывать:

- prompt injection;
- вредоносный контент в найденных документах;
- валидацию вызовов инструментов;
- чрезмерное выполнение инструментов;
- эксфильтрацию данных;
- утечку секретов.

## 15.3 Изоляция данных

Система должна установить чёткие границы между:

- пользовательским вводом;
- найденным контентом;
- системными инструкциями;
- результатами инструментов.

Найденные документы должны рассматриваться как **данные**, а не инструкции.

# 16. Трасса исследования и объяснимость

UI должен предоставлять трассу исследования.

Пример:

```text
Исследование начато

1. get_campaign_metrics()
   Результат: ROI снизился с 2.9 до 1.8

2. compare_segments()
   Результат: снижение сосредоточено среди высокоценных клиентов

3. get_campaign_exposure()
   Результат: охват вырос с 1.4 до 3.7

4. search_campaign_knowledge()
   Результат: найдено 3 исторических случая

5. analyze_exposure_vs_response()
   Результат: сильная отрицательная связь

6. Итоговый синтез
```

Трасса должна раскрывать:

- вызванные инструменты;
- параметры инструментов на подходящем уровне абстракции;
- полученные доказательства;
- найденные документы;
- время выполнения;
- ошибки/повторные попытки;
- итоговое сопоставление доказательств.

## Опциональное отображение цепочки рассуждений

Система может предоставлять опциональную конфигурацию для уместного **резюме рассуждений / визуализации внутреннего анализа** с учётом возможностей и политик выбранного поставщика LLM.

Реализация не должна зависеть от раскрытия приватной цепочки рассуждений.

По умолчанию UI должен показывать **проверяемую трассу исследования**, а не приватные рассуждения модели.

# 17. Методология оценки

Исследование должно сравнить три подхода.

## 17.1 Базовый подход A — Детерминированная аналитика

Реализация с использованием:

- SQL;
- предопределённых бизнес-правил;
- детерминированных расчётов;
- стандартных аналитических запросов.

## 17.2 Базовый подход B — Традиционная ML / статистическая аналитика

Где это уместно:

- классификация;
- регрессия;
- модели склонности;
- кластеризация;
- обнаружение аномалий;
- uplift-моделирование;
- статистические тесты.

Точный метод ML должен зависеть от сценария.

## 17.3 Подход C — AI-агент

Агент может использовать:

- SQL;
- ML/статистические инструменты;
- RAG;
- несколько вызовов инструментов;
- итеративное исследование.

Агент не должен оцениваться как замена базовых аналитических инструментов.

Он оценивается по способности **оркестрировать и синтезировать их**.

---

# 18. Набор данных для оценки

Набор данных для оценки должен содержать примерно десять представительных бизнес-вопросов.

Он должен включать:

1. обычные аналитические вопросы;
2. открытые исследовательские вопросы;
3. вопросы, требующие исторических знаний;
4. вопросы, требующие структурированных и неструктурированных доказательств;
5. вопросы с противоречивыми доказательствами;
6. вопросы, где правильный вывод — «недостаточно доказательств»;
7. известные сценарии с внесёнными эффектами.

---

# 19. Эталонная истина

Для выбранных сценариев должна быть известна эталонная истина.

Пример:

```text
Внесённое условие:
Охват кампании существенно вырос.

Ожидаемая исследовательская гипотеза:
Усталость от кампаний.

Подтверждающее доказательство:
Отклик снижается с ростом охвата.
```

Сценарии с эталонной истиной позволяют объективно измерять:

- обнаружение гипотез;
- поиск доказательств;
- ложноположительные результаты;
- пропущенные объяснения.

Эталонная истина не должна быть доступна агенту во время оценки.

---

# 20. Оценка человеком

Эксперт-оценщик должен оценивать результаты по заранее определённой рубрике.

Рекомендуемые измерения:

| Измерение | Описание |
|---|---|
| Фактическая точность | Подтверждены ли фактические утверждения? |
| Релевантность | Отвечает ли ответ на вопрос? |
| Качество доказательств | Уместны и достаточны ли доказательства? |
| Качество рассуждений | Разумен ли путь исследования? |
| Качество гипотез | Правдоподобны и полезны ли гипотезы? |
| Практическая применимость | Может ли маркетолог действовать по результату? |
| Полнота | Были ли рассмотрены важные источники доказательств? |
| Прозрачность | Явно ли обозначены неопределённость и ограничения? |

Оценки должны быть нормализованы, например по шкале 1–5.

# 21. Количественные метрики оценки

Проект должен измерять:

## 21.1 Качество исследования

- фактическую точность;
- охват доказательств;
- точность гипотез;
- долю полезных инсайтов;
- полезность рекомендаций;
- долю ложноположительных результатов;
- долю неподтверждённых утверждений.

## 21.2 Эффективность

- время до ответа;
- число ручных аналитических шагов;
- число вызовов инструментов;
- число SQL-запросов;
- число найденных документов;
- длительность исследования.

## 21.3 Эффективность ИИ

- вызовы LLM;
- входные токены;
- выходные токены;
- оценочную стоимость LLM;
- стоимость одного исследования;
- среднюю задержку;
- неудачные вызовы инструментов;
- повторные попытки.

## 21.4 Продуктивность бизнеса/аналитика

Где это выполнимо:

```text
Время исследования аналитиком без агента
vs.
Время проверки аналитиком с агентом
```

Цель — не устранить аналитика, а сократить усилия на исследование.

# 22. Результат исследования

Итоговый исследовательский отчёт должен ответить:

1. Где ИИ даёт измеримую ценность?
2. Где SQL остаётся лучше?
3. Где ML остаётся лучше?
4. Какие вопросы получают наибольшую пользу от агентного исследования?
5. Открывает ли агент полезные гипотезы, которые пропускают детерминированные системы?
6. Сокращает ли агент время исследования?
7. Какова доля фактических ошибок?
8. Какова стоимость одного исследования?
9. Какой объём проверки человеком остаётся необходимым?
10. Оправдан ли AI-подход для этого класса бизнес-задач?

Проект должен допускать следующий итоговый вывод:

> **ИИ даёт недостаточную дополнительную ценность.**

Отрицательный результат считается валидным результатом исследования.

# 23. Функциональные требования

## FR-001 — Вопрос на естественном языке

Пользователь должен иметь возможность отправить бизнес-вопрос на естественном языке.

## FR-002 — Планирование исследования

Агент должен определять начальную стратегию исследования.

## FR-003 — Выбор инструментов

Агент должен динамически выбирать аналитические инструменты и инструменты поиска.

## FR-004 — Структурированный анализ

Система должна поддерживать детерминированный анализ на SQL.

## FR-005 — Историческое сравнение

Система должна поддерживать сравнение текущего и исторического периодов.

## FR-006 — Анализ сегментов

Система должна поддерживать исследование клиентских сегментов.

## FR-007 — Сравнение кампаний

Система должна поддерживать сравнение кампаний друг с другом.

## FR-008 — Семантический поиск знаний

Система должна поддерживать семантический поиск маркетинговых документов.

## FR-009 — Многошаговое исследование

Исследование должно поддерживать несколько вызовов инструментов и итеративное уточнение.

## FR-010 — Формирование гипотез

Агент должен формировать явные гипотезы.

## FR-011 — Проверка гипотез

Агент должен пытаться проверять важные гипотезы с использованием доступных аналитических инструментов.

## FR-012 — Рекомендации

Агент должен формировать рекомендации или рекомендуемые следующие исследования.

## FR-013 — Доказательства

Итоговый ответ должен предоставлять доказательства в поддержку основных выводов.

## FR-014 — Неопределённость

Агент должен сообщать о неопределённости и недостаточности доказательств.

## FR-015 — Трасса

Система должна сохранять трассу исследования.

## FR-016 — Оценка

Система должна сохранять метрики, необходимые для исследовательской оценки.

## FR-017 — Абстракция набора данных

Загрузка и логическая модель данных должны поддерживать замену исходного набора данных.

## FR-018 — Абстракция LLM

Система должна позволять менять поставщика LLM без переписывания бизнес-логики.

# 24. Нефункциональные требования

## NFR-001 — Воспроизводимость

Одинаковые версия набора данных, конфигурация и сценарий должны позволять повторяемую оценку.

## NFR-002 — Наблюдаемость

Система должна журналировать:

- выполнения агента;
- вызовы инструментов;
- ошибки;
- задержку;
- использование токенов, где оно доступно;
- метрики оценки.

## NFR-003 — Надёжность

Неудачный вызов инструмента не обязательно должен завершать всё исследование.

Агент должен восстанавливаться после сбоя или сообщать о нём надлежащим образом.

## NFR-004 — Производительность

Для демонстрационных нагрузок система должна обеспечивать разумное интерактивное время ответа.

## NFR-005 — Масштабируемость

Архитектура должна допускать:

- более крупные наборы данных;
- дополнительные инструменты;
- дополнительные наборы данных;
- дополнительных поставщиков LLM;
- больше пользователей.

## NFR-006 — Безопасность

Секреты не должны быть встроены в исходный код.

Доступ к базе данных должен использовать принцип наименьших привилегий.

## NFR-007 — Сопровождаемость

Логика агента, инструменты, доступ к данным, промпты и логика оценки должны быть модульными.

## NFR-008 — Аудитируемость

Исследования должны быть отслеживаемыми после выполнения.

# 27. Требования к генерации синтетических знаний

Синтетические документы должны генерироваться через контролируемый pipeline.

Пример:

```text
Реальные данные кампании
       |
       v
Извлечение фактов кампании
       |
       v
Генерация документа
       |
       v
Проверка фактов
       |
       v
База синтетических знаний
```

Каждый сгенерированный документ должен сохранять ссылки на структурированные сущности, из которых он был получен.

Пример метаданных:

```text
document_id
campaign_id
source_type = synthetic
generation_version
generation_model
source_data_version
created_at
```

Это обеспечивает возможность аудита синтетических знаний.

# 28. Историческое воспроизведение

Поскольку основной набор данных статичен, система должна поддерживать симулированную временную шкалу.

Пример:

```text
Неделя 1
  |
Неделя 2
  |
...
  |
Неделя 70  <-- Агент видит только данные, доступные на этот момент
  |
Неделя 71
  |
...
Неделя 102
```

Агент не должен получать доступ к будущим данным в ходе сценария оценки.

Это обеспечивает:

- бэктестинг;
- временную оценку;
- предотвращение утечки данных;
- реалистичное исследование кампаний.

---

# 29. Предотвращение утечки данных

Фреймворк оценки должен предотвращать:

- раскрытие агенту будущих транзакций;
- извлечение будущих результатов кампаний;
- использование будущих post-mortem-анализов;
- присутствие информации об эталонной истине в промптах/документах.

Это необходимо для достоверной оценки.

---

# 30. Ограничители агента

Агент должен:

- использовать только одобренные инструменты;
- избегать неограниченного выполнения SQL;
- избегать записей в базу данных;
- соблюдать временные границы;
- цитировать доказательства;
- отличать гипотезы от фактов;
- избегать неподтверждённых причинных утверждений;
- выявлять противоречивые доказательства;
- останавливаться после получения достаточных доказательств;
- избегать ненужных вызовов инструментов.

Может быть установлен бюджет исследования:

```text
максимум вызовов инструментов
максимальное время выполнения
максимум найденных документов
максимум вызовов LLM
максимальный бюджет токенов
```

# 31. Оценка стоимости

Каждое исследование должно фиксировать:

```text
Вызовы LLM
Входные токены
Выходные токены
Оценочная стоимость LLM
Запросы к базе данных
Векторные поиски
Время выполнения
```

Исследование должно сравнивать:

```text
Стоимость AI-агента
vs.
Оценочные трудозатраты аналитика
```

Проект не должен предполагать, что технически успешный агент экономически оправдан.

# 32. Оцениваемые режимы отказа

Тестовый набор должен намеренно включать:

Агент должен отказывать **безопасно и прозрачно**.

# 33. Ключевые риски

| Риск | Митигация |
|---|---|

| Чрезмерная стоимость LLM | Бюджеты инструментов/вызовов/токенов |

# 37. Пример эталонного исследования

Представительное исследование должно выглядеть примерно так:

```text
ПОЛЬЗОВАТЕЛЬ

Почему эффективность кампании по возврату клиентов снизилась
за последние три месяца?


АГЕНТ

1. Установить базовый уровень эффективности кампании.

   -> get_campaign_metrics()

   ROI:
   Исторический: 2.9
   Текущий:      1.8


2. Выявить затронутые сегменты.

   -> compare_segments()

   Высокоценные клиенты: -22%
   Клиенты средней ценности: -8%
   Низкоценные клиенты: +2%


3. Исследовать охват кампании.

   -> get_campaign_exposure()

   Средний охват:
   Исторический: 1.4
   Текущий:      3.7


4. Сформулировать гипотезу:

   Усталость от кампаний может способствовать снижению.


5. Найти исторические знания.

   -> search_campaign_knowledge()

   Найдены три исторически похожих случая.


6. Проверить гипотезу.

   -> analyze_exposure_vs_response()

   Отклик заметно снижается при повторяющемся охвате.


7. Синтезировать доказательства.

   Текущие структурированные данные и исторические
   post-mortem-анализы кампаний показывают согласованный паттерн.


8. Рекомендация.

   Проверить уменьшенную частоту кампаний для высокоценных
   клиентов с помощью контролируемого эксперимента.


9. Оговорка.

   Доказательства подтверждают связь, но не устанавливают причинность.
```

# 38. Архитектурный принцип

Проект должен следовать одному центральному архитектурному принципу:

Этот принцип центральный для исследовательской гипотезы.

# 39. Ожидаемое отличие от традиционной BI-системы

Традиционная BI-система отвечает на предопределённые вопросы:

```text
Что произошло?
Сколько?
Когда?
Где?
Какой сегмент?
```

ML-система отвечает на предиктивные вопросы:

```text
Что, вероятно, произойдёт?
Кто, вероятно, уйдёт?
Кто, вероятно, откликнется?
Каков ожидаемый uplift?
```

AI Campaign Investigator работает с другим классом вопросов:

```text
Почему это может происходить?
Какие прошлые ситуации на это похожи?
Какие гипотезы стоит исследовать?
Какие доказательства подтверждают или опровергают каждую гипотезу?
Что следует исследовать дальше?
```

Ценность агента заключается именно в том, что путь исследования **не полностью задан заранее**.

# 40. Итоговый исследовательский принцип

Проект не должен быть разработан для доказательства полезности ИИ.

Он должен быть разработан, чтобы определить, **где ИИ полезен, где он не полезен и оправданы ли дополнительная сложность и стоимость**.

Поэтому ожидаемый вывод должен быть выражен через границы принятия решений, например:

> Используйте SQL для детерминированных измерений.

> Используйте ML для предиктивной оптимизации.

> Используйте статистические методы для проверки гипотез и причинного анализа.

> Используйте AI-агента, когда задача требует динамического исследования разнородной структурированной и неструктурированной информации.

Следовательно, итоговый результат — не просто AI-приложение.

Это **оценка на основе доказательств того, являются ли AI-агенты экономически и технически оправданным инструментом для исследования бизнес-задач программ лояльности.**
